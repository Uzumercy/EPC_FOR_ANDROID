## 1. REUSE.CD（147,662 バイト）— 純正品番 ↔ リユース（中古）部品の対応表

### 1.1 フォーマット
バイナリではなく **cp932 の固定長テキスト**。全行同長で CRLF 終端。

- 1 行 = 84 文字 + CRLF、**1,717 行**。84×86 = 147,662 でファイルサイズと完全一致。
- フィールド配置（文字位置は 0 始まり）:

| 範囲 | 内容 |
|---|---|
| `[0:11]` | 純正品番（11 桁 = 5+3+3。全 1,717 行がこの形に一致） |
| `[11:13]` | 純正品番のサフィックス（2 文字。`ZZ` 514 行、`ZA`/`ZE`/`ZF` 等の色コード系、空白 415 行） |
| `[13:24]` | **REUSE 品番** = `R` + 4 桁 + 3 桁 + 3 桁（11 文字） |
| `[24:26]` | REUSE 側のサフィックス欄（2 文字。§1.3） |
| `[26]` | 定数 `4`（全行同一。§1.3） |
| `[27:34]` | 価格（右詰め 7 文字）。数値 1,716 行、「ｵｰﾌﾟﾝ」（オープン価格）1 行 |
| `[34:55]` | 品名＋適用注記（21 文字、左詰め）。例：`R.ﾌﾛﾝﾄ ﾄﾞｱ (EL,ML,)`、`L.ﾍﾂﾄﾞﾗｲﾄ`。`R.`/`L.` は左右、括弧内は適用グレード |
| `[55:59]` | 種別表記 `ﾁﾕｳｺ`（チュウコ＝中古。全行固定位置） |
| `[59:84]` | 空白 |

### 1.2 検証結果
- REUSE 品番は、純正品番の主番号先頭 4 桁＋中 3 桁＋後 3 桁から作られる
（主番号 5 桁目が落ちる）。同一部品の対応では A 欄と一致するが、
**140 行は A 欄と異なる部品由来**（例：`04670-SR4-A00` ↔ `R6701-SR4-305B`）で、
「別品番の部品が中古として流用可能」という対応付けも含む。
- A 欄の純正品番のうち DISC1 の PLMST に存在するのは 871 件（残りは DISC2 側の
車種・部品。SR4 系シビック等）。
- 価格は PLMST の純正価格と **871 件中 0 件一致**（全て異なる）。
→ REUSE 独自の価格（中古価格）であることの根拠。
- プログラム側の根拠：`HMEPCDAT.DLl` に `EpcFindReuseByHop` / `EpcFindReuseByReuse` /
`EpcFindHopByReuse` / `EPCLOADREUSEDATA` のエクスポートがあり、
純正品番（HOP）⇔ REUSE 品番の双方向引きが本家機能として存在する。
`HMEPCBHN.DLl` には `EPCPTISREUSEPOSSIBLE` と設定キー
`HANBAITEN_ReuseIsPossible` 等があり、販売店設定でリユース可否を切り替える
機能に結びついている。

### 1.3 未解決点
- `[24:26]` の REUSE 側サフィックス欄の意味：値の分布は `BZ` 1,158 行、空白 238 行、
`B ` 165 行、`ZA` 19 行、`ZE` 17 行、`ZD`/`ZF`/`ZH` 等。
`Z`+英字は A 欄サフィックス（色コード）と同じ様式で色コードの可能性があるが、
頻出の `BZ` の意味（色コードか状態区分か）はデータだけでは確定できなかった。
- `[26]` の定数 `4`（HAMP.CD と共通）：価格区分・四輪区分等の候補はあるが未確定。
- `[55:59]` の表記は 2 種類のバイト列が混在する（`ﾁｭｳｺ` 780 行 / `ﾁﾕｳｺ` 937 行。
小さい ュ と大きい ユ の違いのみで、読みは同じ「チュウコ」）。

## 2. HAMP.CD（149,132 バイト）— 純正品番 ↔ HAMP 品番の対応表

### 2.1 フォーマット
REUSE.CD と同じ骨格の **cp932 固定長テキスト**。

- 1 行 = 90 文字 + CRLF、**1,621 行**。90×92 = 149,132 で完全一致。
- フィールド配置:

| 範囲 | 内容 |
|---|---|
| `[0:11]` | 純正品番（11 桁。1,492 行が 5+3+3 形に一致。残り 129 行はプラグ等の社外型番形式、例：`9807B5615P`） |
| `[11:13]` | 空白 |
| `[13:24]` | **HAMP 品番** = `H` + 4 桁 + 3 桁 + 3 桁（11 文字。末尾グループが 2 文字＋空白になるプラグ系もある） |
| `[24:26]` | 空白 |
| `[26]` | 定数 `4`（REUSE と共通） |
| `[27:34]` | 価格（右詰め 7 文字、全行数値） |
| `[34:59]` | 品名＋ブランド名（25 文字）。例：`ﾊﾟﾂﾄﾞｾﾂﾄ,ﾌﾛﾝﾄｼﾑｸﾞﾘｽﾅｼHAMP`、`ｲﾘｼﾞｳﾑﾌﾟﾗｸﾞ2(ZFR6FI)HYPER`。末尾にブランド名（HAMP / HYPER）が付く |
| `[59:84]` | 空白 |
| `[84:86]` | メーカーコード欄：HYPER ブランドのバルブ／プラグ行（172 行）のみ `SH`、他は空白 |
| `[86:90]` | 空白 |

### 2.2 検証結果・役割
- DISC1 の PLMST に A 欄の品番が存在するのは 591 件。価格はそのうち
8 件のみ PLMST と一致し、583 件は異なる → HAMP 独自の価格表。
- プログラム側の根拠：`HMEPCDAT.DLl` に `EpcFindHampByHop` / `EpcFindHampByHop2` /
`EpcFindHampByHamp` / `EpcFindHopByHamp` / `EPCLOADHAMPDATA`、
`HMEPCFIL.DLl` に `EPCWKSETUPHAMPTOPLM`（HAMP を部品リストへ組み込む処理）、
`HMEPCBHN.DLl` に `EpcPTHampKousuuChangeDlgProc`（HAMP 工数変更ダイアログ）と
`EPCPTSELECTEDHAMPBUHIN` がある。
→ 本家 EPC では、部品明細の純正品番を HAMP 品番（補修用ブランド部品）に
置き換えて表示・見積もる機能があり、その対応表が本ファイル。
HAMP はブレーキパッド等の補修部品ブランド、HYPER はバルブ／プラグの
ブランドで、`SH` はそのメーカーコードと推定される（確定はできていない）。

## 3. KRHHDKI.CD（8,127 バイト）— 型式コード → KSRBHMH ブロック索引

### 3.1 フォーマット（従来説の訂正を含む）
- **21 バイト固定ではない。可変長レコード**のチェーン（先頭 u16LE = レコード全長で
辿るとファイル末尾に完全一致）。**315 レコード**。
- レコード = `[u16LE 全長][型式コード 11 バイト（ASCII、空白詰め）][(u32LE オフセット, u32LE バイト長) × n]`
- レコード長は 21/29/37/45/53 バイト（n = 1〜5）。分布：n=1 が 185 件、2 が 90 件、
3 が 25 件、4 が 11 件、5 が 4 件。

### 3.2 検証結果
- 315 件全ての (オフセット, バイト長) ペア列が、KSRBHMH 内でその型式コード
（レコード bytes 37..44）を持つレコードの**連続ブロック列と完全一致**した。
例：`AA` → (907919, 4967) = CITY E-AA の 45 レコードのブロック。
- 型式コードの種類数も KSRBHMH 側と一致（315 種）。
- 役割：本家の「打刻型式から車両を特定」する導線の索引であることが、
推定ではなく全件突合で確定した。

## 4. KRHHKI.CD（13,026 バイト）— 型式フル＋類別番号 → KSRBHMH ブロック索引

### 4.1 フォーマット
- **26 バイト固定 × 501 レコード**。
- `[0:13]` 型式フル（ASCII、空白詰め。例：`AAA-ZE1`、`E-AA`）
- `[13:18]` 類別番号（ASCII 数字、空白詰め）。**5 桁（新型式、例：`12220`）と
4 桁（旧型式、例：`4441`）が混在**する。
- `[18:22]` u32LE：KSRBHMH 内の当該型式フルの連続ブロックのバイトオフセット
- `[22:26]` u32LE：そのブロックのバイト長

### 4.2 検証結果
- 500 件の通常エントリ全てが KSRBHMH の型式フル別ブロックと完全一致。
- 類別番号は、ブロック先頭レコードの KSRBHMH フィールド `[2:7]`（code1）と
**500 件全て一致**（例：E-AA の類別 `4441` = CITY レコードの code1）。
- レコード 0 は型式・類別とも空欄で (0, 551) を持ち、KSRBHMH 先頭の
型式フル空欄レコード群（ACTY VAN / CIVIC GX の 5 レコード、551 バイト）を
指す正規エントリとみられる（ダミーではない）。
- KSRBHMH の型式フル別ブロックは全部で 501 個あり、本ファイルが全てをカバーする。
- 役割：本家の「型式類別から車両を特定」する導線の索引（確定）。
なお本ファイルは PLMST 適用コードの参照先ではない（従来の棄却済み仮説どおり）。

## 5. HPLTBLJH.CD（20 バイト）— ルート.CD ファイルのサイズ表

### 5.1 フォーマット
- u16LE の値列 10 個。ルートの基幹.CD ファイル 8 本の**ファイルサイズ**を、
固定順序で記録したもの。
- 並び順は `HMEPCFIL.DLl` 内のファイル名リスト順：
`TSMIR.CD`(16,401) / `KRHHKI.CD`(13,026) / `KRHHDKI.CD`(8,127) /
`KSRBHMH.CD`(3,073,097) / `SYSBMST.CD`(3,460) / `GRPBRTBL.CD`(396) /
`IMTBL.CD`(122,760) / `CDJHTBL.CD`(17)。
- サイズは u16LE の低位ワードで記録され、65,536 以上のファイル
（KSRBHMH、IMTBL）では続けて u16LE の高位ワードが置かれる
（KSRBHMH = 低位 58,441 + 高位 46、IMTBL = 低位 57,224 + 高位 1）。
- 対象外は `REUSE.CD` / `HAMP.CD` と本ファイル自身。REUSE/HAMP には
`HMEPCFIL.DLl` に専用のサイズ取得関数（`EpcDTGetFileSizeREUSE/HAMP`）があり、
別経路で扱われることと整合する。

### 5.2 検証結果・未解決点
- 上記 8 ファイル全ての実サイズと一致（検証スクリプトで確認）。
- 役割は、CD データの整合性チェック用マニフェストと推定される
（`HMEPCDAT.DLl` に `EPCDTGETHPLTBLJH` のエクスポートがある）。
- 参考：カタログ側の同名系統 `PLBTBLJH.CD`（B班担当）も同じ方式のサイズ表で、
11SA702 の全 13 ファイルの実サイズと一致することを本検証で確認した。
ただし PLBTBLJH では中央の 9 ファイル（BLKTYTBL、PLMSBBI1/2、PLMKSBI1/2、
PLMST、PLGKTBL、PLCKTBL、KCMST）がサイズ 65,536 未満でも常に
低位＋高位（=0）の 2 ワード形式だった。ルート側は 65,536 以上の
ファイルだけが 2 ワード形式であり、「どのファイルが 2 ワード形式か」の
設計規則は 2 例からは一意に決まらない。読み手はファイル一覧と実サイズを
知った上で照合する前提のテーブルである。

## 6. TSMIR.CD（16,401 バイト）— 通称名 → KSRBHMH ラン索引

### 6.1 フォーマット
- 可変長レコードのチェーン（先頭 u16LE = 全長で末尾に完全一致）。**105 レコード**。
- レコード = `[u16LE 全長][通称名 15 バイト（ASCII、空白詰め）][エントリ × n]`
- エントリ = 21 バイト固定：`[型式フル 13 バイト][u32LE オフセット][u32LE バイト長]`
- レコード長 = 17 + 21n（38, 59, 80, 101, 122, 143, 185, 269,...）。
エントリ総数は **696 件**。

### 6.2 検証結果
- 696 件全ての (オフセット, バイト長) が、KSRBHMH 内で
「その型式フル」かつ「その通称名（車名フィールド）」を持つレコードの
連続ランと完全一致した。
例：通称名 `ACCORD AERODECK` の `E-CA1` エントリ (1038297, 5170) は、
E-CA1 ブロック（233 レコード）の中で車名が `ACCORD AERODEC` の
46 レコードのランを指す。
- 注意：KSRBHMH の車名フィールドは 14 文字で切れる（`ACCORD AERODEC`）ため、
照合は TSMIR 側の通称名を 14 文字に切り詰めて行う。
- 役割：本家の「通称名から車両を特定」する導線の索引（確定）。

## 7. IMTBL.CD（122,760 バイト）— 色コード → 色名表

### 7.1 フォーマット
- **66 バイト固定 × 1,860 レコード**（122,760 = 66×1,860 で割り切れる）。
- `[0:10]` 色コード（ASCII、空白詰め）。例：`AG`、`BEIGEM`、`BG1L`、`BG13M`、
`NH…`（637 件と最多）、`YR…`、`B…`、`R…`、`PB…` 等、色系統の頭文字で始まる。
- `[10:16]` 枝番（ASCII、空白詰め）。値の例：`1`（205 件）、`2`（50 件）、
`L`（38 件）、`3`（16 件）、`R`（8 件）、`3L`、`02M` 等。空白が 1,443 件。
- `[16:66]` 色名（cp932 半角カナ 50 バイト、空白詰め）。
例：`AG` → ｱﾐｭｰｼﾞﾝｸﾞｸﾞﾚｰﾒﾀﾘｯｸ、`BG1L` → ﾀｰｺｲｽﾞﾌﾞﾙｰ。
- (色コード, 枝番) の組は全 1,860 件で一意。同一コード・同一色名で
枝番だけが違う行がある（例：`BG1L` の空白行と `1` 行は同じ色名）。

### 7.2 検証結果・未解決点
- 全件パース可能で、コード重複は枝番で区別されることを確認した。
- 色名が空欄のレコードが 109 件ある（コードは `TYPEA`、`TYPEB`、`TYPEAG` 等）。
内装色のタイプ指定用のコードと推定されるが、意味は未確定。
- 枝番の意味（内装/外装の区別か、色コードの世代か）は未確定。
- 役割：車両特定時の内装色・外装色コード→色名の表示、および前文
「色記号と色名」の元データ（`HMEPCFIL.DLl` のロード対象に含まれる）。

## 8. GRPBRTBL.CD（396 バイト）— ルート側グループ目次マスタ

### 8.1 フォーマット
- **44 バイト固定 × 9 レコード**。
- `[0:2]` グループ番号（ASCII、例：`1 `、`2 `）
- `[2:41]` グループ名称（cp932 39 バイト、空白詰め）
- `[41:44]` グループコード（ASCII 3 文字。`E `、`EAT`、`EMT`、`F `）
- 内容：1 エンジン (E) / 2 ミッション（ＡＴ） (EAT) / 2 ミッション（ＡＴ） (EAT) /
2 ミッション（ＭＴ） (EMT) / 3 電装／吸排気／ヒーター (F) /
4 ｽﾃｱﾘﾝｸﾞ/ﾌﾞﾚｰｷ/ｻｽﾍﾟﾝｼｮﾝ (F) / 5 艤装 (F) / 6 車体 (F) / 7 オプション (F)

### 8.2 検証結果・備考
- カタログ別 `GRPTBL.CD`（54 バイトの長さプレフィックス付きレコードで、
名称・コードの後に 8 バイトのリンクフィールドを持つ）と同じ内容系統だが、
本ファイルはプレフィックスもリンクも持たない 44 バイト固定形式で、

書式の解釈違いではないことをバイト位置で確認済み。

## 10. 残課題（A班範囲）
- REUSE.CD `[24:26]` サフィックス欄と両ファイル共通の定数 `[26]` = `4` の意味。
- HAMP.CD `[84:86]` の `SH` の正式な意味（メーカーコードと推定）。
- IMTBL.CD の枝番 `[10:16]` と色名空欄 109 件（TYPE 系コード）の意味。
- HPLTBLJH の「2 ワード形式になるファイル」の設計規則（§5.2）。
- いずれも構造・件数・他ファイルとの整合は確定済みで、残るのは意味づけのみ。

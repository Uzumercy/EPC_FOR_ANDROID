# B班 解析レポート：カタログ内ファイル群（IBHTBL / PLBTBLJH / KCMST / PLGKTBL / PLCKTBL / MBMJTBL）

対象は DISC1 ISO（11CD081）の各カタログフォルダ内に置かれた `.CD` ファイル6種。
全82カタログ（IBHTBL のみ81カタログ）について、実データで構造を確定し、
全件パース＋ファイル末尾一致の検証を行った。検証は
`analysis/verify_b_catalog.py` で再実行でき、全項目パスする（`ALL CHECKS PASSED`）。
探索過程のスクリプトは `analysis/explore_*.py` に残した。

表記：バイト範囲は Python スライス形式 `[a:b]`、多バイト整数は特に断らない限り LE。

---

## 1. MBMJTBL.CD ― 前文（諸注意ページ）目次

### フォーマット

可変長レコードの連鎖（先頭2バイト＝レコード全長 u16LE、辿ると EOF に一致）。

| 範囲 | 内容 |
|---|---|
| `[0:2]` | レコード全長（u16LE） |
| `[2:4]` | ページコード（ASCII 2文字） |
| `[4:34]` | タイトル（30バイト固定、cp932、空白パディング） |
| `[34:]` | ファイルコード（10バイト ASCII × n、空白パディング） |

レコード長 = 34 + 10n（n = そのページの画像ファイル数、通常1、標準整備時間は複数）。

> **既存レポートの訂正**：`EPC_FORMAT_REPORT.md` §3.7 は「44バイト固定レコード」と
> していたが、実際は可変長である。44バイトは n=1 の場合の長さにすぎない
> （例：シティの「標準整備時間」は4ファイルあるため74バイト）。

### ページコードとタイトル（全82カタログ集計、延べ374レコード）

| コード | タイトル | 出現カタログ数 |
|---|---|---|
| `10` | 号機管理 | 81 |
| `20` | 色記号と色名 | 81 |
| `30` | 部品名欄の略語 | 82 |
| `40` | 特別仕様車 | 45 |
| `90` | 標準整備時間 | 82 |
| `15` | 型式類別番号・装備表 | 2 |
| `45` | パッケージ・その他 | 1 |

- `10`/`20` を欠くのは `116790J1`（ACTY TRUCK）のみで、同カタログの前文は
「部品名欄の略語」「標準整備時間」の2ページだけである。
- タイトルは cp932 で文字化けなくデコードできる（半角カナ問題なし）。

### ファイルコードと実ファイルの対応（全件検証済み）

- ファイルコードは、サブディレクトリ `M` 内の実ファイル名から `.` を除いた文字列である。
例：コード `4JSA71001` ↔ ファイル `4JSA7100.1`。
- 全82カタログで、MBMJTBL のファイルコード総数 **939件** と
`M` フォルダの実ファイル総数 **939件** が **集合として完全一致**（過不足0）。
- コード→ファイル名の復元は「末尾から1〜3文字の前に `.` を挿入」で行うが、
挿入位置はカタログにより異なる（`11S0601` は末尾2文字前：
コード `4JS0610101` ↔ `4JS06101.01`）。一意に決めるには `M` フォルダの
実ファイル一覧と「`.` 除去」で突き合わせるのが確実である。

### front_matter テーブル化仕様（Windows版コンバーター向け）

```
front_matter(catalog TEXT, page_code TEXT, title TEXT, seq INT,
file_code TEXT, file_name TEXT)
```
- 1レコード＝（ページ × ファイル）で1行。`seq` はレコード内のファイル順（0始まり）。
- `file_name` は `M` フォルダ実在ファイルとの突合で確定した名前を格納する。

### 検証結果

- 82カタログ全てで長さチェーンが EOF に一致、レコード長規則
（34 + 10n）違反 0 件、ファイルコード照合 939/939 一致。

## 2. PLBTBLJH.CD ― カタログ内ファイルのサイズ照合表

今回もっとも綺麗に解けたファイル。**44バイト固定**、全82カタログに存在する。

### フォーマット

| 範囲 | 型 | 内容（＝そのカタログフォルダ内のファイルサイズ） |
|---|---|---|
| `[0:2]` | u16LE | GRPTBL.CD |
| `[2:4]` | u16LE | BLKTBL.CD |
| `[4:8]` | u32LE | BLKTYTBL.CD |
| `[8:12]` | u32LE | PLMSBBI1.CD |
| `[12:16]` | u32LE | PLMSBBI2.CD |
| `[16:20]` | u32LE | PLMKSBI1.CD |
| `[20:24]` | u32LE | PLMKSBI2.CD |
| `[24:28]` | u32LE | PLMST.CD |
| `[28:32]` | u32LE | PLGKTBL.CD |
| `[32:36]` | u32LE | PLCKTBL.CD |
| `[36:40]` | u32LE | KCMST.CD |
| `[40:42]` | u16LE | IBHTBL.CD（無いカタログでは 0） |
| `[42:44]` | u16LE | MBMJTBL.CD |

- 対象は自カタログフォルダ内の他の `.CD` ファイル **13種すべて**
（PLBTBLJH 自身と図ファイルは含まない）。
- 小型テーブル4種（GRPTBL / BLKTBL / IBHTBL / MBMJTBL）は u16、
大きくなりうる9種は u32 で格納される、という混在幅が実データの形である。

### 検証結果

- **全82カタログで全13項目が実ファイルサイズと完全一致**。
唯一の例外扱いは `12SZ001` で、同カタログには IBHTBL.CD が存在せず、
格納値も 0 になっており矛盾しない。

### 役割

- カタログデータの完全性／版数チェック用のサイズ表とみられる。
CD更新プログラム（HMEPCSU）やロード時の検証で使うためのものと推定されるが、
参照側プログラムの確定はしていない。
- 読み違い注意：先頭4バイトを u32 と読むと `0x00C801B0` のような無意味な
大数になるが、実際は u16 × 2（GRPTBL 432 + BLKTBL 200、シティの場合）である。
末尾4バイトも同様（IBHTBL 1141 + MBMJTBL 206）。

## 3. KCMST.CD ― 工数（標準整備時間）マスタ

### フォーマット

可変長レコードの連鎖（EOF一致）。

| 範囲 | 内容 |
|---|---|
| `[0:2]` | レコード全長（u16LE）＝ 57 + 60n |
| `[2:52]` | 品名（50バイト固定、cp932、空白パディング） |
| `[52:57]` | 工数値（5バイト ASCII、右詰め。形式は後述） |
| `[57:]` | 注記ブロック（60バイト cp932 × n、空白パディング） |

- 全82カタログで **102,010レコード**、注記ブロック総数 **18,370**。
レコード長規則（57 + 60n）違反は全カタログで 0 件。
- シティ（11SA702）は 1,769レコード（ファイル 119,253バイト）。

### 工数値フィールドの文法

| 形式 | 件数（全82） | 意味 |
|---|---|---|
| `8.1` のような数値（小数1桁） | 97,250 | 工数（時間） |
| `#1.7`（`#`＋数値） | 3,546 | 脚注記号付き工数（後述） |
| `*12.0`（`*`＋数値） | 667 | 脚注記号付き工数（後述） |
| `-` | 489 | 自前の工数を持たない参照エントリ |
| （空白） | 58 | 値なしエントリ（8カタログのみ） |

- 数値はすべて小数1桁（0.1時間＝6分単位）。シティ分の分布は 0.1〜8.1
（`*` 付きを含めると最大 12.0）、最頻は 0.2 / 0.3 / 0.1 の順。
- `-` のエントリの品名は「ｶﾝﾚﾝﾌﾞﾋﾝﾉ ﾌﾞﾛｯｸｻﾝｼﾖｳ（関連部品のブロック参照）」
「ﾊﾞﾝｷﾝ/ﾄｿｳｺｳｽｳﾋﾖｳｻﾝｼﾖｳ（板金/塗装工数表参照）」
「ﾄﾘﾂｹｺｳｽｳﾊ ｱｸｾｻﾘｰｶﾀﾛｸﾞｦ ｻﾝｼﾖｳ」等で、**参照先を見る指示そのもの**が
品名として入っている。
- 空白値のエントリは `11SB201` の「ﾄﾞﾗｲﾌﾞｼﾔﾌﾄｾｯﾄ,L.」等のセット品に集中する。
理由は未確定（セット構成品側に工数が付く形式のためと推定）。

### 注記ブロック

シティ分で41種の注記テキストが確認できた。代表例：

- `( ｶﾝﾚﾝﾌﾞﾋﾝ ﾌｸﾑ)`（関連部品含む）×191
- `( ﾄｿｳﾘﾖｳｷﾝ ﾌｸﾏｽﾞ)`（塗装料金含まず）
- `(ﾀｰﾎﾞﾂｷ 0.2ｶｻﾝ)`、`( ｲﾂｺﾏｼ 0.2 ｶｻﾝ)`（1個増し0.2加算）、
`(ｶﾀｶﾞﾜﾂｲｶ 1.3 ｶｻﾝ)`（片側追加1.3加算）、
`( ﾆﾘﾝ ｻﾕｳｾｲﾋﾞｼﾞﾊ 1.2 ﾄｽﾙ)`（二輪左右整備時は1.2とする）、
`( ﾊﾞﾙﾌﾞｼﾕｳｾｲ ﾌｸﾑ)` / `( ﾊﾞﾙﾌﾞｼｰﾄﾉ ｼﾕｳｾｲ ﾌｸﾏｽﾞ)` 等

これらは標準整備時間表に典型的な工数調整注記であり、疑う余地がほぼない。

### 役割が「工数（標準整備時間）」である根拠

1. 注記がすべて工数の加算・包含関係の指示である（上記）。
2. 数値が時間として自然な粒度（0.1単位）で、小物部品は 0.1〜0.5、
トランスミッション内部部品（ｷﾞﾔｰ,ﾒｲﾝｼﾔﾌﾄ等）は 7.0〜7.5、
ｹｰｽ,ﾄﾙｸｺﾝﾊﾞｰﾀｰ 8.1、ｼﾘﾝﾀﾞｰﾌﾞﾛｯｸ *12.0 と、
「脱着＋分解を伴う作業ほど大きい」という工数の大小関係と一致する。
3. `-` エントリが「塗装工数表参照」等、整備時間表の参照指示になっている。
4. 前文ページに「標準整備時間」（MBMJTBL コード `90`）が全カタログに存在し、
本家画面の部品明細にも「工数」欄がある（UI_NOTES 参照）。
5. 棄却した代替仮説：重量（kg）説は、ﾎｰｽ1本 8.1kg や ｵｲﾙｼｰﾙ 7.3kg が
成り立たず、注記の「加算」表現とも合わないため棄却。
価格説は PLMST 側に価格が別にあるため棄却。

### PLMST 部品との対応付け

- キーは**品名**である。ただし PLMST の品名そのままではなく、
「ベース品名」―― PLMST 品名から (1) 先頭の1文字区分、
(2) `*色コード*` 部分、(3) `(メーカー名等)` の括弧書きを取り除いた形。
- シティでの検証：この正規化で KCMST のユニーク品名 1,268件中
**1,214件（95.7%）** が PLMST 品名と一致した。残りの大半は
`Oﾘﾝｸﾞ` 系の表記差（サイズ表記の揺れ）である。
- 逆方向のカバー率は 35.1%（PLMST ベース品名 3,457種中 1,214種）。
工数が定義されるのは作業単位になる部品だけで、全品名には付かない。
- **同名異値**：シティで306品名が複数エントリを持ち、大半は同値の重複だが、
異値の例もある（例：`ﾌﾟﾚｰﾄ,ｵｲﾙｶﾞｲﾄﾞ` = 7.6 / 7.6 / 0.4）。
KCMST レコードには図・ブロックへの参照が一切ないため、
「どの図の文脈の工数か」はレコード単体では決められない。
- **並び順**：KCMST の並びは PLMST の出現順とは一致しない
（一致したエントリ 1,694件で隣接逆転 273件）。標準整備時間表側の
作業順に並んでいるとみられる。

### 未解決点

- `#` / `*` の脚注記号の定義。シティの `#` 付き18件は全てエアコン部品
（ｺﾝﾌﾟﾚｯｻｰASSY.、ｺﾝﾃﾞﾝｻｰASSY.、ｴﾊﾞﾎﾟﾚｰﾀｰ等）で、
`#` がエアコン関連の区分であることは強く示唆される。`*` は
ｼﾘﾝﾀﾞｰﾌﾞﾛｯｸ（*12.0）、ｸﾗﾝｸｼﾔﾌﾄ（*11.0）等のエンジン本体作業に付く。
凡例は前文「標準整備時間」ページ（画像）側にあるとみられ、
M フォルダ図のデコード（C班）での照合が次の手。
- 同名異値の使い分け規則（原本プログラムが図の文脈でどう選ぶか）。
- 空白値エントリ（58件）の意味。

## 4. PLGKTBL.CD ― 号機範囲の辞書

### フォーマット

**17バイト固定レコード**、全82カタログで **63,572レコード**。

| 範囲 | 内容 |
|---|---|
| `[0:1]` | 区分キー（ASCII 1文字、全カタログで `C` / `E` / `F` / `M` のみ） |
| `[1:9]` | from（8バイト、空白パディング） |
| `[9:17]` | to（8バイト、空白パディング） |

- from / to は号機（フレーム番号等）の文字列。数字のみの号機は
右詰め気味（先頭に空白）、英数字フレーム（後述）は左詰めで格納される。
- from・to の両方が空白のレコードは存在しない（全件検証）。
内訳：to のみ 27,659件 / from のみ 28,057件 / 両方 7,856件。
- レコードは（キー、from、to）の順にソートされている。
- 区分キー別の件数：`F` 45,860 / `E` 10,830 / `M` 6,802 / `C` 80。

### 解釈

- レコードは号機範囲 `[from, to]` を表す。from 空白は「〜to」
（紙カタログの「〜1200000」表記）、to 空白は「from〜」（「1300001〜」表記）
に対応する形である。
- 値の粒度はモデルマスタの号機帯よりはるかに細かい。シティでは
PLGKTBL の distinct 値 938種に対し、モデルの号機帯は12種しかなく、
モデル帯の境界値（1000001、1200000、1400000 等）に加えて
1000193 / 1000194 のような**実生産の変更点そのもの**の号機が並ぶ。
つまり本表は「そのカタログで部品適用が切り替わる号機の区切り辞書」である。
- 区分キーは号機の種別とみられる：`E`＝エンジン号機、`F`＝フレーム号機、
`M`＝ミッション号機と読むと、件数配分（F が最大）や、シティの `M` 区分に
5xxxxxx〜9xxxxxx の多様な帯があることと整合する。ただしこれは推定であり、
確定には前文「号機管理」ページ（MBMJTBL コード `10`）の図との照合が要る。
`C` は12カタログ（1168005、11SB001、11SB601、11SC902、11SD501、11SD511、
11SF101、11SH201、11SH301、11SH401、11SH501、11SJ701）にのみ現れる
第4の種別で、意味は未確定。

### 英数字フレームへの対応

モデルのフレーム番号が英数字混在のカタログでは、from / to に
そのまま英数字のフレーム識別子が入る。例：

- `11SB001`：`VF01A C`、`VF01B D` 等（識別子＋1文字の区分）
- `11SD201` / `11SJ401`：`P1000001`、`P1031839` 等（英字1字＋数字7桁）
- `11SD401`：`G1000000`、`L2000175` 等
- `11SB601` / `11SC902`：`EA12A`、`EA13B` 等

このため from / to は「7桁数字」ではなく「最大8文字の号機文字列」として
扱うのが正しい。

### 棄却した仮説

- 「[ブロック記号10B][号機7桁] の単独レコードと [ブロック][from][to] の
2形式混在」説：シティで 1,036件中 693件が前者に一致しないことから
混在に見えたが、`[1B][8B][8B]` の統一レイアウトで全63,572件が
例外なく説明できるため、混在説は棄却し統一レイアウトを確定とした。
- 「キーは GRPTBL のグループコードの頭文字」説：全82カタログ中
一致は1カタログのみで棄却。
- 「キーは PLMST のブロック記号」説：シティの PLMST ブロックは
ATM / B / BOP / E / M で、PLGKTBL のキー E / F / M とは
`F` の有無や ATM・B・BOP の欠落が合わず棄却。

### 未解決点

- 区分キー（特に `C`）の正式な意味。
- 原本プログラムが PLMST の適用情報（モデルID方式）から本表を
どう参照するか。本表自体に部品・図への参照は含まれない。

## 5. PLCKTBL.CD ― 括弧書き注記用語のマスタ

### フォーマット

- **20バイト固定スロット**の列。長さチェーンは持たない。
全82カタログでファイルサイズが20で割り切れ、総スロット数 **1,772**。
- 各スロットは `(用語)` の形の文字列（cp932、半角カナ主体）＋空白パディング。
- 並びは読みの五十音順で、その後に英数字で始まる用語が続く。
- シティ（31件）の例：`(ｱﾜｾｶﾞﾗｽ)`、`(ｶﾝﾚｲﾁ)`、`(ｼﾞｮｼｭｾｷｶﾞﾜ)`、
`(ﾄﾞｱｰﾐﾗｰ)`、`(ﾇﾉｾｲ ﾎﾞﾃﾞｲｿﾆﾂｸ)`、`(ﾈｯｾﾝﾂｷ)`、`(ﾋﾀﾞﾘｳｴ)`、`(ﾌﾛﾝﾄ)`、
`(ﾏｽﾀｰﾊﾟﾜｰﾂｷ)`、`(ﾘﾔｰﾜｲﾊﾟｰﾅｼ)`、`(ﾙｰﾌｻｳﾝﾄﾞ)`、`(130Rﾖｳ)`、
`(36000-PC0-921)` 等。仕様・装備・部位を表す注記用語である。
- 例外1件：`11SD201` のスロット13 `(P.W.ｼﾖｳﾊﾋﾀﾞﾘｶﾞﾜﾆｼﾖｳ` は
用語が21バイトあり、20バイトに切り詰められて閉じ括弧を欠く。
全1,772スロット中でこの1件だけが `(用語)` の形にならない（原データ由来）。

### 試した仮説と棄却理由

1. **「そのカタログの PLMST 品名に現れる括弧書きの一覧」説 → 棄却。**
シティで31用語中、PLMST 品名（生バイト列・NFKC正規化の両方）に
現れるのは1件のみ。逆方向でも、PLMST 品名の括弧セグメントは
485種あり大半が PLCKTBL にない。
2. **「PLMST 尾部 B型グループの注記本文」説 → 棄却。**
尾部の注記参照は `(1)`〜`(8)` の番号のみで、PLCKTBL の用語とは
一致しない（シティで照合、一致0件）。
3. **「BLKTYTBL タイトル／KCMST／GRPTBL に現れる用語」説 → 棄却。**
`11SB001` で全数照合し、出現0件（PLMST のみ36件中3件が偶然一致）。

### 残る知見と未解決点

- 内容はカタログごとに異なり（全82カタログで内容の重複なし）、
その車種の仕様・装備に関わる注記用語であることは確かである。
- プログラム側では `HMEPCFIL.DLL` のファイル一覧に他のデータファイルと
並んで登録されているだけで、用途の手がかりは得られなかった。
- 印刷（紙カタログ形式）時の仕様注記や、原本の注記表示系で使う
用語マスタというのが残る候補だが、データ側からは参照元を
特定できなかった。**役割は未確定**として残す。

## 6. IBHTBL.CD ― 色記号テーブル

81カタログに存在し、`12SZ001` にのみ無い（PLBTBLJH のサイズ欄も 0）。

### フォーマット

可変長レコードの連鎖（EOF一致）。全81カタログで **2,318レコード**。

| 範囲 | 内容 |
|---|---|
| `[0:2]` | レコード全長（u16LE） |
| `[2:12]` | キー（10バイト ASCII、空白パディング） |
| `[12:14]` | 後続文字数＋2（u16LE） |
| `[14:]` | 文字集合（ASCII 大文字、ソート済み、重複なし） |

レコードはキー文字列のバイト順にソートされており、2つのセクションからなる。

### セクション1：キー空白＋文字集合あり（683レコード）

- キーは10バイトすべて空白。文字集合は1文字以上の集合。
- シティでは文字は `{B, G, N, O, S, U, V, W, Y}` の部分集合で、
単独文字のレコードが全種そろい、複合集合
（例：`BGNOSUVW`、`BGNUWY`）が辞書順に並ぶ。
組み合わせ表のような形をしている。
- 全カタログ通算では文字集合に A〜Z の全文字が現れる（カタログごとに部分集合）。

### セクション2：色記号キー＋文字集合なし（1,635レコード）

- キーは色記号（例：シティでは `B21M`、`B26M`、`G55`、`NH61`、`NH79M`、
`NH82`、`PB67`、`R37Z`、`R39`、`Y44Z` 等）。文字集合は常に空。
- ルートの色コード表 `IMTBL.CD` と照合すると、1,635件中
**1,543件（94.4%）** が IMTBL 内に文字列として存在した。
残りは `NH583MT`、`B74PY` のような複合形と、
`NH82/YR68M` のようなツートーン（`/` 区切り）形が大半で、
これらも色記号の組み合わせと読める。
- よってセクション2は「そのカタログで使われる外装色記号の一覧」で確定としてよい。

### 未解決点

- セクション1の文字集合の意味。1文字コードの集合であること、
カタログごとに文字種が変わることから、内装色系のコード集合というのが
候補だが、キー（空白）との対応関係を説明できておらず未確定。
- ファイル全体の原本での用途（車両特定時の色入力検証か、
色付き部品の表示用か）は特定できていない。
- 棄却した仮説：「文字集合＝その色記号に付く内装色」という読みは、
色記号キー側のレコードでは文字集合が常に空であるため棄却。
セクション1と2は別々の小テーブルが連結したものとみるのが自然である。

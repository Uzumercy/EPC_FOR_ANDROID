### 項目1b: 同名異値（シティ306品名）の使い分け規則 — 進展あり

検証方法: BLKTYTBL 尾部の KCMST 区間（図サブ単位のスライス）で KCMST レコードを図ごとに切り分け、「カタログ全体では複数値を持つ品名」が「各図の中では単一値になるか」を全82カタログで数えた（`analysis/d_data.py`）。

結果:
- 複数値を持つ品名は全カタログ合計 **5,653品名**。
- うち **5,183品名（91.7%）は、図（サブ）ごとに切り分けると各図内では単一値**になり、かつ図によって値が異なる。例（116790J1）: ﾒｲﾝｼﾔﾌﾄ は ATM の図で *5.2、M（MT）の図で *4.1。つまり同名異値の大半は「図（＝ブロック・バリエーション）ごとに工数が決まる」ことで説明できる。
- 残り **470品名** は同一図内でも複数値を持つ。（品名, 図）の組で数えると514組あり、うち365組はレコードに注記が併記され条件が区別できる（例: ターボ付き加算）。注記なしで同名異値の組もあり（例: 1168005 B-17-2 ﾎｰｽ,ｳｵｰﾀｰｲﾝﾚﾂﾄ 1.2 / 0.3）、これらは同名の別部品（部位違い等）が同じ代表品名で載っているケースとみられる。

限界: KCMST レコードには図以外の識別子（部品番号・見出番号）がなく、PLMST との対応は代表品名ベースでしか取れない（B班の突合で PLMST 側カバー率 35.1%）。したがって「同じ図・同じ品名・注記なし」の複数値を個々の部品へ1対1に割り当てる規則は、DISC1 のデータ内には存在しない。

## 項目3: IBHTBL.CD 第1節の意味 — 進展あり（構造訂正あり）

### B班報告の訂正

B班の「第2節はキー＋空の文字集合」という記述はシティ（11SA702）だけを見たための誤り。全カタログで再分類すると:

- レコードは全て [len][キー 10B][文字数+2 u16][文字集合] で、キー付きレコードにも文字集合がある（例: 11S0601 B92P → 'D' / 'DK' / 'K' の3レコード）。
- ファイル冒頭には**キー空白のレコード群**があり、その文字集合は「そのファイルのキー付きレコードで使われる文字集合の種類」と一致する場合がある（IBHTBL を持つ80カタログ中10カタログで完全一致。11S0601 では冒頭3件 {D, DK, K} = キー付き側の相異なる文字集合と一致）。
- ただし56カタログではキー付き側の文字集合が全て空で、冒頭の文字集合群だけが存在し（例: シティは冒頭53件 {B, BG, BGNOSUVW, ...}、キー付き15件は全て空）、残り14カタログは冒頭群とキー付き側の集合が部分的にしか重ならない。

### 分かっていること

- IBHTBL は色部品用データ。HMEPCDAT のエクスポート `EPCDTGETIROBUHIN`（色部品）が対応する（項目5）。色名そのものは IMTBL（`EPCDTGETCOLORDATA`）側。
- キー付きレコードのキー = 外装色の本田色記号。ツートン複合形（NH82/YR68M 等）や末尾バリエーション文字（B74PY の Y、B92PS の S、NH583MT の T、NH538W の W）を含む形でも収録される。PLMST の部品名に現れる色コード（*NH82* 等）とも対応する。
- 文字集合の字母は1文字の「タイプ」識別子。プログラムの車両特定画面では内装色を「内装色 (Type)」と表示し（HMEPC.EXe メイン画面、HMEPCBHN の文字列「内装色ﾀｲﾌﾟ」）、IMTBL には色名を持たない `TYPEA` / `TYPEAG` / `TYPEBK` のような「TYPE＋字母」の色記号が多数存在する。字母集合は「その外装色と組み合わさる内装色タイプの集合」と読むのが最も自然で、キー付きレコードの実例（同一外装色 B92P に対して D / DK / K と複数レコード = 型式類別ごとに組み合わせが違う）とも矛盾しない。

### 限界

- 字母1文字が具体的にどの内装色タイプを指すかは、カタログごとに前文「色記号と色名」ページの組み合わせ表（外装色/内装色一覧表、ツートンアンダー色組み合わせ表など、画像 `analysis/work/d_pages/11S0601_4JS06201.0*.png`）と対応付ける必要があるが、表側に字母そのものは印刷されておらず、データ内での対応表は見つからなかった。
- 冒頭のキー空白レコード群が「何をキーとして」並んでいるか（型式類別順か、内装色順か）は特定できていない。棄却した仮説: PLMST 部品番号サフィックス文字の集合（81カタログ中27のみ包含）、PLMST 色部品の枝番文字の集合、外装色記号の頭文字の集合（シティの字母 {B,G,N,O,S,U,V,W,Y} には外装色の頭文字にない O,S,U,V,W が含まれる）。
- したがって第1節は「内装色タイプの組み合わせ表である可能性が高い」ところまでが根拠のある範囲で、**字母の意味づけはここが限界**。

## 項目4: PLGKTBL.CD の区分キー `C` — 確定

**`C` = キャブレター型式番号（キャブロットNo）の号機区切り。**

根拠: 前文ページコード10（号機管理表）に「キャブレター型式番号」の列があり、PLGKTBL の `C` レコードの値と完全一致する。
- 11SB001（プレリュード E-AB）の号機管理表（画像 `analysis/work/d_pages/11SB001_4JSB0100.1.png` / `.2.png`）: キャブレター型式番号 = VF01A [C]、VF01B [C,D]、VF01C [D]、VF01D [E]…。PLGKTBL の `C` レコードは ('', 'VF01A C')、('', 'VF01B C')、('VF01A D', '') 等で、表の値そのもの。
- 同表で BA1（PGM-FI 車）のキャブレター欄は「(PGM-FI)」とだけあり、キャブレター装着車にのみ型式番号が存在することと一致する。脚注にも「キャブレターアッセンブリーはエンジン号機で管理されていますが、その構成部品はキャブレター型番で管理されています」とある。
- プログラム側にも裏付けがある: HMEPCBHN に「キャブロットNo選択」ダイアログ（DLG 127）と `EPCPTCABROTNOADDDLGPROC` があり、部品特定の過程でキャブレターのロットNoを選ばせる画面が実在する。

これで PLGKTBL のキーは E=エンジン号機 / F=フレーム号機 / M=ミッション号機 / C=キャブレター型式番号 の4種で全て確定した。`C` が現れる12カタログ（1168005, 11SB001, 11SB601, 11SC902, 11SD501, 11SD511, 11SF101, 11SH201, 11SH301, 11SH401, 11SH501, 11SJ701）は全てキャブレター装着グレードを含む車種（プレリュード、シビック系、バラード、トゥデイ、アクティ）である。

ついでに: `M` の英数字値（11SB001 等4カタログ、128件）は号機管理表のミッション号機表記「GM-3000001〜」「AK-6000001〜」「A1C5-1000001〜」に対応する英字プレフィックス付き号機で、PLGKTBL にはプレフィックスを除いた／含んだ表記が混在する。`E` / `F` は全カタログで数字のみだった。

- REUSE のサフィックスは値のパターン（1文字目が B または Z、2文字目が A〜Z または空白）がパーツ色記号（ZA, ZB…）の体系に似るが、REUSE 品番側に付く理由・意味を裏付ける資料はデータ内になかった。

結論: 3点とも意味づけの根拠が DISC1＋FD の範囲内に存在せず、**ここが限界**。`SH` は「HYPER 行のメーカーコード」という位置づけ（A班）以上には進められない。

## 項目7: サイズ表（HPLTBLJH / PLBTBLJH）の2ワード形式の規則 — 進展あり

A班の未解決「64KiB 以上のファイルだけ2ワードになるのか、それ以外の規則か」に対する検証（全82カタログの実サイズで確認）:

- PLBTBLJH の **u16 スロット**（GRPTBL / BLKTBL / IBHTBL / MBMJTBL）の実サイズは全カタログを通して最大でも GRPTBL 432B / BLKTBL 200B / IBHTBL 1,539B / MBMJTBL 488B。64KiB には遠く及ばない。
- 一方 **u32 スロット**のファイルには PLGKTBL（最小34B）や PLCKTBL（最小60B）、PLMSBBI1（最小730B）のような小さなファイルも含まれ、実際のサイズに関係なく u32 幅が割り当てられている。

したがって規則は「実行時にサイズを見て切り替える」ものではなく、**ファイル種別ごとに固定のレイアウト**であることが確定した。HPLTBLJH で u32 なのが KSRBHMH（3,073,097B）と IMTBL（122,760B）だけなのは、ルート側ではその2つが「64KiB を超えうるファイル」として設計時に選ばれた結果と読める。PLBTBLJH では中核データ9ファイル（BLKTYTBL、索引×4、PLMST、PLGKTBL、PLCKTBL、KCMST）が一括で u32、補助マスタ4ファイル（GRPTBL、BLKTBL、IBHTBL、MBMJTBL）が u16 という種別分けになっている。

「なぜその種別分けか」という設計意図そのもの（読み込み方式の違い等）は資料がなく、ここまでが根拠のある範囲。

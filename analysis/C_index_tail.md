# C班 解析結果：索引系・BLKTYTBL尾部・PLMST尾部残件・M図デコード検証

対象：DISC1 ISO（11CD081）の全82カタログ。検証スクリプトは `analysis/c_*.py`、抽出物は `analysis/work/` に残した。既存DB・コンバーター本体は変更していない。

## 1. 索引ファイル群 PLMKSBI1/2・PLMSBBI1/2（全82カタログ）— 完全解読

### 1.1 「1」と「2」の違い（確定）
DISC1/DISC2用でも予備でもない。**「1」=バケットディレクトリ（上位索引）、「2」=索引本体**の2段構成。

### 1.2 PLMSBBI（部品番号索引）
- **PLMSBBI1.CD**：10バイト固定レコード ×n。
  `[主部品番号の先頭2文字（ASCII 2B）][u32LE: PLMSBBI2内のバイトオフセット][u32LE: バイト長]`
  オフセットは累積で連続し、長の合計は PLMSBBI2 のファイルサイズと全82カタログで一致。
- **PLMSBBI2.CD**：可変長レコードの連鎖。
  `[u16LE 全長][主部品番号5桁（ASCII 5B）][エントリ×n]`
  エントリは6バイト固定：`[u32LE: PLMST.CD内のバイトオフセット][u16LE: そのPLMSTレコード長]`。
  全長 = 7 + 6n（全レコードで成立）。
- キーは主部品番号（部品番号の先頭5桁）。同一主番号の全レコードが1レコードにまとまる。

### 1.3 PLMKSBI（部品名索引）
- **PLMKSBI1.CD**：10バイト固定。キーが「品名の先頭2バイト（cp932）」である以外は PLMSBBI1 と同形式。
- **PLMKSBI2.CD**：可変長レコード。
  `[u16LE 全長][品名キー10バイト][エントリ×n]`、エントリは PLMSBBI2 と同じ6バイト（PLMSTオフセット＋レコード長）。
  品名キー = PLMSTテキストブロックの名前部分先頭10バイト（レコード byte 25〜34。byte 24 は空白）。
  全長 = 12 + 6n。名前が10バイトで切れるため、接頭辞が同じ別名部品も同じレコードに混ざる（例：シティ `ｱｰﾊﾟｰﾈﾙCOMP` のレコードには 31206-PA0-005 / -PE0-005 / -PA0-006 等が入る）。

### 1.4 検証結果（`c_verify_index.py`、全82カタログ）
| 索引 | バケット数 | レコード数 | エントリ総数 |
|---|---|---|---|
| PLMSBBI | 6,551 | 234,028 | 609,952 |
| PLMKSBI | 14,104 | 179,811 | 609,952 |

- 両索引とも、**全PLMSTレコード 609,952 件をちょうど1回ずつ参照**（過不足・重複なし）。
- 全エントリについて「オフセットが実在のPLMSTレコード先頭と一致」「レコード長が一致」「キーがそのレコードの主番号／品名接頭辞と一致」を確認。**問題 0 件**。
- つまり本家プログラムの「部品番号一覧」「部品名一覧」検索はこの索引で PLMST を引いており、我々の逆引き（全件走査＋自前索引）と同じ結果になることが裏付けられた。

### 1.5 未解決点（軽微）
- レコードの並び順はバケット内では本家のコレーション（かな読み順）で、バイト順ではない（例：PLMKSBI では ASCII 名がかな名より後、PLMSBBI では `061C1` が `06141` より前）。正確な照合順序表は未解明だが、索引の意味・ポインタの正しさには影響しない。
- グループ内エントリの並びは、PLMSTオフセット順・部品番号順・品名順・図キー順のいずれでもないことを確認した（本家ビルド時の挿入順と推定）。

## 2. BLKTYTBL.CD 尾部 — 大部分解読

### 2.1 レコード構造（確定分）
```
[u16LE 全長][図キー7B][図面コード10B][タイトル50B（解読済み）]
[u32LE PLMSTオフセット][u32LE PLMST長]
[u32LE KCMSTオフセット][u32LE KCMST長]
[u16LE 第1リストのバイト長 L1][第1リスト: u16×(L1/2)]
[第2リスト: u16×残り全部]
```

### 2.2 オフセット対の検証（`c_verify_blkty.py`、全82カタログ・全15,291レコード）
- **PLMSTオフセット／長**：その図（ブロック＋図番＋サブ）の部品レコードが PLMST 内に占める区間と**全件一致**。区間はファイル全体を過不足なく連続して覆う。
- **KCMSTオフセット／長**：その図の KCMST.CD 内区間。シティ（11SA702）では全237図で「区間内を u16 長チェーンでちょうど歩き切れる」ことと、区間の合計が KCMST ファイルサイズ（119,253）と一致することを確認。先頭図 ATM 1 の区間は 57バイトレコード×7。
  - 例外2件：11S2R01 の B 8 で 57バイト、11SR401 の E 1 で 969バイト（=57×17）の隙間がある。どちらの隙間も57の倍数で、BLKTYTBL のどの図からも参照されない KCMST レコードが存在する（図タイトルを持たない区間の存在）ことを示す。
- これにより「KCMST は図単位で区切られたファイル」であることが確定した（内容の解析はB班担当）。

### 2.3 コードリスト部
- 第2リストは**全15,291件で常に昇順ソート済み**（構造の裏付け）。
- 第2リストと、その図の PLMST 部品の適用コード（尾部グループのコード）との突合：
  - 和集合（union）と一致：8,360件
  - 各部品のコード集合の積集合（intersection）と一致：6,920件
  - 上記の残り：11件（第2リストが空で、積集合は空でないケース）
  - ※和集合＝積集合になる図は和集合側に数えた。単一パターンしかない図では両者は一致する。
- 第1リスト：長さは 2バイト（13,848件）／4バイト（1,307件）／6バイト（130件）／8バイト（6件）。値もモデルIDの範囲内。
- 長さ89バイトの最小レコード（シティで78件）はコード部が `02 00 02 00`（第1リスト=[2]、第2リスト=空）で、その図の部品コード積集合が空になる図と対応する。

### 2.4 未解決点
- **第1リストの意味は未解明**。棄却した仮説：
  - 「第2リストから除外されたコード」— 反例：シティ E-1（サブなし）では第1リスト [96] が第2リストにも含まれる。
  - 「その図の和集合に含まれないコード」— 反例：同 [96] は和集合に含まれる。ただし E-1 サブ2 の第1リスト [14] は自図の和集合に無く、兄弟バリアント E-1（サブなし）の和集合には含まれる例もあり、「兄弟バリアント側のコード」という仮説は完全には棄却できていない。
- 第2リストが和集合と積集合のどちらに一致するかは図によって異なり、単一の生成規則（パターン数など）では説明できなかった。本家が図の表示可否判定に使う「図自体の適用範囲」として独立に持たれているデータとみるのが妥当で、PLMST 側からの完全な再構成はできない、というのが現時点の結論。

## 3. PLMST尾部の残件

### 3.1 パース失敗247件 — 全件救済（文法拡張を提案）

失敗は全609,952件中247件（0.04%）。失敗レコード一覧は `analysis/work/tail_failures.tsv`。

**主因（大半）**：B型グループの注記参照欄が**固定3バイト**であるのに対し、現行パーサは `)` を探す実装になっている。注記番号が2桁になると欄は `(14` のように `)` が収まらず、パースが落ちる。
- 例：11S0501 B 15 品目25（91902-SJ8-003）— A型2グループの後、B型 `(14`、`(8)` が続く。
- 注記参照の総数調査（拡張パーサによる）：`(1)` 28,490件、`(2)` 3,695、`(4)` 3,555、`(N)` 1,567、`(3)` 979、`(5)` 574、`(6)` 543、`(16` 214、`(8)` 77、`(7)` 62、`(9)` 26、`(10` 30、`(12` 14、`(11` 9、`(14` 9、`(20` 8、`(18` 5、`(25` 1、`(26` 1。注記番号は 1〜26 と `(N)` が存在する。

**その他の変種**（残り約20件）：
- 注記欄が `12)` / `32)`（数字＋閉じ括弧のみ。11SA702 B 16 品目38/40）。現行パーサは `)` 検索で偶然処理できている。
- 3バイト欄が数量・注記のどちらでもないもの（全 corpus で23グループのみ）：空白のみ `   ` ×11、` N ` ×4、` 6 ` / ` 1 ` / ` 4 `（数量の後ろ空白型）×4、`Y01` `Y03` `E01` ` L1` ×各1。

**拡張文法**（`c_tail_generic.py` で検証）：
> グループ = `[u16LE 全長][4バイト][3バイト欄][u16LEコード列…]`。欄の解釈は後付けとし、欄が数量形式なら数量、括弧を含めば注記、それ以外はそのまま保持する。コードは常にグループ先頭+9から始まり、(全長−9) は偶数。

- 結果：**609,952件 全件パース成功**。
- 現行パーサで解釈できていた 609,705 件については、**解釈の変更 0 件**（数量・コード列が完全一致）。後方互換な拡張としてコンバーターへ取り込むことを提案する（C班では本体に手を入れていない）。

### 3.2 B型注記の「本文」の所在 — DISC1データ内には見つからず

探した場所と結果：
- **PLMST.CD**：括弧は品名内部の表記（例：`ｸﾗﾂﾁｴﾝﾄﾞ (1)(2.3MM)` の厚み区分）のみ。注記文なし。
- **PLCKTBL.CD**：括弧書き用語のリスト（(ｱﾜｾｶﾞﾗｽ) 等）で、番号注記の本文ではない。
- **KCMST.CD**（シティ全件走査）：括弧は品名の継続表記（( ｶﾝﾚｲﾁ ﾂｷ ) 等）のみ。
- **BLKTYTBL / BLKTBL / GRPTBL / PLGKTBL / PLBTBLJH / IBHTBL**：本文を格納できる大きさ・文字列なし。
- **索引ファイル群**（§1）：ポインタのみで本文なし。
- **ルート11ファイル**（パターン走査）：番号注記・文末表現（`。`）とも検出なし。HAMP.CD / REUSE.CD は代替部品の互換データで注記ではない。
- **MBMJTBL.CD の目次**（複数カタログ）：項目は 号機管理／色記号と色名／部品名欄の略語／特別仕様車／標準整備時間 のみで、「注記一覧」に相当する前文項目は無い。
- **図ファイル**：セグメントは画像（'2'/'3'）とホットスポット（'C'）のみで、テキストセグメントは存在しない（§4 のセンサスで確認）。
- **ISO の README.TXT**：版の案内文のみ。
- **FD側プログラム**（exp7z 展開済みバイナリ群）：`注記` の文字列自体が無い。

未調査として残るもの：
- **CD側プログラム（HMEPCAT.EXE / HMEPCDAT.DL_ 等、SZDD圧縮）**：この環境に 7z が無く展開できなかった。FD側（リビジョン71）には注記文が無いが、CD側 v4.40 のデータDLLに標準注記文が埋め込まれている可能性は否定できない。
- **DISC2**：手元に無いため未確認（注記はカタログ＝DISC単位のデータのはずなので、可能性は低いとみる）。

結論：注記番号 1〜26＋(N) に対応する本文は、DISC1 のカタログデータ内にはテキストとして存在しない。Windows版要件の「注記はマーカー表示まで」という決定（2026-11-16）とこの結果は整合する。

## 4. Mフォルダ図ファイルのデコード検証 — 全件成功

### 4.1 結果（`c_verify_m.py`、全82カタログ）
- Mフォルダのファイルは全 **939件**。全件がセグメント構成 **`2C`**（画像セグメント種別 '2' ＋ 'C' セグメント）。
- 数字サブフォルダの部品図 15,270 件は全件 **`3C`**。種別文字は「前文ページ='2'／部品図='3'」できれいに分かれる。
- **デコード成功 939/939（100%）**：既存方式（セグメント先頭+11/+13 の u16BE で幅・高さ、+21 から終端までを CCITT Group 4 ストリームとして TIFF ラッパー＋PIL で展開）がそのまま使える。種別 '2' でも形式は同一だった。
- **ホットスポットは全件 0 件**：'C' セグメントは長さ4の空テーブル（ヘッダのみ）。前文ページにクリック対象は無い。
- 目視確認したサンプル（`analysis/work/m_samples/`）：
  - 11SA702 `4JSA7100.1`（号機管理）：AA-150 の R ハイパーシフト（記載タイプ R7）を含む表が判読可能。
  - 11SA702 `4JSA7200.1`（色記号と色名）、`4JSA7900.4`（標準整備時間・定期点検時整備時間早見表）：いずれも表として完全に読める。

### 4.2 コンバーターへの含意
前文画像の取り込みは「デコード対象のサブフォルダに M を追加する」だけで済む。幅・高さ・ストリーム位置とも部品図と同じで、特別な処理は要らない。
